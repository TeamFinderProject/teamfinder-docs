# ADR-001. Механизм аутентификации

- Статус: Принято
- Дата: 20.10.2026
- Автор: Участник 1 (Backend)
- Связано с: `api-contracts-v1.md`, разделы 3 и 4

ADR (Architecture Decision Record) — короткая запись архитектурного решения: какая была проблема, какие варианты рассматривали, что выбрали и почему.

## Контекст

На checkpoint 2 механизм входа был записан как «будет выбран позже». Без него нельзя реализовать ни одну защищённую операцию: backend должен понимать, кто делает запрос, чтобы назначить владельца проекта, проверить, что заявку принимает владелец, и так далее.

Требования:

1. Frontend — SPA на React, backend — ASP.NET Core Web API. В dev-режиме они на одном origin (прокси Vite), в Docker — тоже за одним адресом.
2. Пользователь не должен вводить пароль заново после перезагрузки страницы.
3. Украденный токен должен жить недолго, а выход из системы — реально завершать сессию.
4. Решение должно быть понятным и объяснимым на защите, без внешних сервисов.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Cookie-сессия (ASP.NET Core Cookie Authentication) | Просто, logout сразу работает | Нужна защита от CSRF для всех изменяющих запросов; сессия держится на сервере; хуже подходит для будущих клиентов, например мобильного приложения |
| B. Один долгоживущий JWT в `localStorage` | Очень просто | Токен доступен любому JS на странице (XSS); отозвать до истечения нельзя; logout ничего не отзывает |
| C. Короткий JWT access + refresh token с ротацией | Access проверяется без обращения к БД; refresh хранится в HttpOnly-cookie и недоступен JS; logout и кража обрабатываются отзывом refresh token | Больше кода: таблица refresh-токенов, endpoint `/refresh`, повтор запроса на frontend |
| D. Внешний провайдер (Keycloak, Auth0) | Готовые функции | Лишняя инфраструктура для учебного проекта, сложнее запуск и защита |

## Решение

Выбран вариант C.

- Access token — JWT, HMAC-SHA256, живёт 15 минут. Claims: `sub` (id пользователя), `email`, `jti`, `iat`, `exp`, `iss`, `aud`. Передаётся в заголовке `Authorization: Bearer`. Frontend хранит его только в памяти.
- Refresh token — 32 случайных байта (base64url), живёт 14 дней. Отдаётся в cookie `tf_refresh` с флагами `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/api/auth`. В таблице `refresh_tokens` хранится только SHA-256 хеш. Флаг `Secure` выключается только для локальной разработки по `http://localhost` (`Jwt:SecureCookie=false`).
- Ротация. `POST /api/auth/refresh` отзывает предъявленный токен и выдаёт новый с тем же `FamilyId`.
- Повторное использование отозванного токена считается признаком кражи: отзываются все токены семейства.
- Logout отзывает текущий refresh token и удаляет cookie.
- Окно 30 секунд после ротации (`Jwt:RefreshReuseGraceSeconds`). Если открыто две вкладки, они могут обновить токен почти одновременно, и вторая придёт со старым токеном. В первые 30 секунд после замены такой токен ещё принимается, позже — считается кражей.
- Защита от перебора паролей: не больше 10 попыток входа в минуту с одного IP (`Jwt:LoginAttemptsPerMinute`), дальше `429 TOO_MANY_ATTEMPTS`. Используется штатный rate limiter ASP.NET Core.
- Пароли — `PasswordHasher<User>` из ASP.NET Core Identity (PBKDF2-HMAC-SHA512, соль и число итераций хранятся внутри хеша).
- Ключ подписи — из конфигурации `Jwt:SigningKey` (не менее 32 байт). В репозитории есть только ключ для разработки в `appsettings.Development.json` и демо-ключ по умолчанию в `docker-compose.yml`, чтобы проект запускался без настройки. Для общего сервера ключ задаётся переменной окружения `Jwt__SigningKey` (в Docker — `JWT_SIGNING_KEY` в `.env`).

## Таблица `refresh_tokens`

| Поле | Тип | Назначение |
|---|---|---|
| `Id` | bigint PK | |
| `UserId` | bigint FK → users | Владелец токена |
| `TokenHash` | varchar(64), UNIQUE | SHA-256 от токена в hex |
| `FamilyId` | uuid | Цепочка ротации, одна на вход |
| `CreatedAt` | timestamptz | |
| `ExpiresAt` | timestamptz | `CreatedAt + 14 дней` |
| `RevokedAt` | timestamptz NULL | Когда отозван (ротация, logout, кража) |
| `ReplacedByTokenId` | bigint NULL | Какой токен выдан взамен при ротации |

## Последствия

- Защищённые endpoint'ы помечаются `[Authorize]`, текущий пользователь берётся из claim `sub`. Передавать `userId` в запросах для действий от своего имени не нужно и нельзя.
- CSRF для API не нужен: access token приходит в заголовке, который чужой сайт подставить не может. Cookie используется только для `/api/auth/refresh` и `/api/auth/logout` и защищена `SameSite=Strict`.
- Frontend при старте вызывает `/api/auth/refresh`, на ответ `401` выполняет одно обновление токена и повторяет запрос.
- Тот же access token подойдёт будущим клиентам, например мобильному приложению. Telegram-боту токен не нужен: он привязывается к аккаунту по одноразовому коду.
- Ограничение: выданный access token нельзя отозвать до истечения 15 минут. Для учебного проекта это приемлемо. Если понадобится мгновенный отзыв, можно добавить проверку `jti` по чёрному списку.
