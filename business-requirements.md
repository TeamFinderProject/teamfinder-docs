## 1. Назначение документа

Документ фиксирует бизнес-контекст TeamFinder: какую проблему решает продукт, кто им пользуется, какие цели преследует первая версия и какие ограничения приняты командой.

Документ отвечает на вопрос «что и зачем», но не описывает, как именно это реализовано. Детализация вынесена в отдельные документы:

- функциональные требования — `functional-requirements.md`;
- бизнес-правила — `business-rules.md`;
- сценарии использования — `use-cases.md`;
- модель данных — `erd-v1.md`;
- архитектура — `architecture-v1.md`.

## 2. Описание проблемы

Поиск команды для pet-проектов, хакатонов и учебных проектов сегодня происходит неструктурированно: через знакомых, тематические Telegram-чаты, форумы и случайные объявления. Информация не структурирована, требования к участникам не формализованы, отклики теряются в переписке.

Проблема проявляется с двух сторон.

### 2.1 Сторона кандидата

Человек хочет участвовать в проекте, но ему нужен не любой проект, а такой, где:

- тема проекта интересна;
- реально открыта подходящая ему роль;
- его навыки соответствуют требованиям роли.

В объявлении обычно нет структурированных требований, поэтому кандидат не может заранее оценить, подходит ли он, и тратит время на нерелевантные отклики.

### 2.2 Сторона создателя проекта

У автора идеи есть потребность в конкретных специалистах: Backend Developer, Frontend Developer, Designer, DevOps. Ему нужно:

- заранее определить состав ролей и количество мест;
- зафиксировать обязательные и желательные навыки для каждой роли;
- получать отклики именно на конкретную роль;
- сравнивать кандидатов по понятным критериям, а не по свободному тексту сообщения.

### 2.3 Последствия

- долгий и хаотичный подбор участников;
- нерелевантные отклики;
- потеря заявок в переписке;
- непрозрачный выбор кандидата;
- неясный статус набора — непонятно, открыт он или уже закрыт.

## 3. Пользователи и заинтересованные лица

| Роль | Описание | Основной интерес |
|---|---|---|
| Кандидат | Зарегистрированный пользователь, который ищет проект и подаёт заявки | Найти подходящий проект и роль, понимать свои шансы |
| Владелец проекта | Пользователь, создавший проект | Собрать команду под конкретные роли и требования |
| Участник команды | Кандидат, принятый на роль | Видеть состав команды, статус проекта, способ связи |
| Гость | Незарегистрированный посетитель | Понять, что за сервис, и зарегистрироваться |

Роли не являются взаимоисключающими: один и тот же пользователь может быть владельцем одного проекта и кандидатом в другом.

Владелец проекта и участник команды — разные понятия. Владелец не занимает место в наборе автоматически.

## 4. Бизнес-цели продукта

| ID | Цель |
|---|---|
| BG-1 | Сделать поиск проекта и поиск участников структурированным процессом вместо переписки в чатах |
| BG-2 | Перенести требования с уровня проекта на уровень конкретной роли |
| BG-3 | Дать кандидату понятное объяснение, насколько он соответствует роли |
| BG-4 | Дать владельцу проекта управляемый процесс рассмотрения заявок и формирования команды |
| BG-5 | Сделать состояние набора и проекта явным и однозначным для обеих сторон |

## 5. Бизнес-требования

### 5.1 Профиль и навыки

| ID | Требование | Приоритет |
|---|---|---|
| BR-1 | Пользователь должен иметь профиль с информацией о себе, интересующими ролями и навыками | MUST |
| BR-2 | Для каждого навыка пользователь указывает уровень владения: начинающий, средний, продвинутый | MUST |
| BR-3 | Уровень навыка является самооценкой пользователя и не проверяется системой | MUST |
| BR-4 | Навыки и типы ролей выбираются из общего справочника; произвольные навыки в первой версии не создаются | MUST |

### 5.2 Проекты и роли

| ID | Требование | Приоритет |
|---|---|---|
| BR-5 | Пользователь должен иметь возможность создать проект с названием, описанием и типом | MUST |
| BR-6 | Поддерживаемые типы проектов: pet-проект, хакатон, учебный проект | MUST |
| BR-7 | Требования к участникам задаются на уровне роли проекта, а не на уровне проекта целиком | MUST |
| BR-8 | Для роли указываются количество мест, обязательные и желательные навыки, при необходимости минимальный уровень навыка | MUST |
| BR-9 | Роль может быть создана без обязательных навыков | MUST |
| BR-10 | Проект должен иметь явное состояние жизненного цикла, определяющее доступные действия | MUST |

### 5.3 Поиск и сопоставление

| ID | Требование | Приоритет |
|---|---|---|
| BR-11 | Пользователь должен видеть каталог проектов с фильтрами по роли, навыку, типу проекта и открытости набора | MUST |
| BR-12 | Система должна сопоставлять профиль пользователя с требованиями конкретной роли | MUST |
| BR-13 | Результат сопоставления должен быть объяснимым: по каждому обязательному и желательному навыку видно совпадение | MUST |
| BR-14 | Сопоставление носит рекомендательный характер и не блокирует подачу заявки | MUST |
| BR-15 | В первой версии не используются ML и процентная оценка соответствия | MUST |

### 5.4 Заявки и команда

| ID | Требование | Приоритет |
|---|---|---|
| BR-16 | Кандидат подаёт заявку на конкретную роль и может приложить комментарий | MUST |
| BR-17 | Владелец видит профиль кандидата, его навыки, уровни, комментарий и результат сопоставления | MUST |
| BR-18 | Владелец принимает или отклоняет заявку; решение принимает человек, а не система | MUST |
| BR-19 | Кандидат может отозвать свою заявку, пока она ожидает решения | MUST |
| BR-20 | Заявка и участие в команде — разные сущности; история заявок сохраняется | MUST |
| BR-21 | Количество принятых участников на роль не может превышать количество мест | MUST |
| BR-22 | Участник может выйти из команды, владелец может исключить участника | MUST |
| BR-23 | Принятый участник получает доступ к странице команды и внешнему контакту | MUST |
| BR-24 | Встроенный чат не реализуется; связь команды осуществляется по внешней ссылке | MUST |
| BR-25 | Пользователь видит список своих заявок и их текущие статусы | SHOULD |
| BR-26 | Владелец видит количество новых заявок по своим проектам | SHOULD |
| BR-27 | Пользователь может указать ссылку на GitHub или портфолио | NICE TO HAVE |

## 6. Ценность explainable matching

Ключевая особенность TeamFinder — объяснимое сопоставление вместо непрозрачной оценки.

Вместо показателя вида «87% соответствия» пользователь видит разбор по критериям:

```
Обязательные навыки:
  Go          — есть, уровень достаточный
  PostgreSQL  — есть, уровень достаточный
Желательные навыки:
  Docker      — есть
  Redis       — нет
Итог: 2 из 2 обязательных, 1 из 2 желательных
```

Почему это выбрано для первой версии:

- пользователь понимает, чего именно ему не хватает, и может дополнить профиль;
- владелец проекта видит основание для решения и может сравнивать кандидатов;
- команде не нужно обосновывать формулу, веса и пороги;
- логика реализуема и проверяема без ML.

Процентная оценка не исключена, но отнесена к будущим версиям.

## 7. Границы первой версии

### 7.1 Входит в v1

- регистрация, вход, выход, права доступа;
- профиль, информация о себе, интересующие роли, навыки и их уровни;
- справочники навыков и типов ролей;
- создание и редактирование проекта, тип проекта, состояние проекта;
- роли проекта, количество мест, обязательные и желательные навыки, минимальный уровень;
- каталог проектов и фильтры;
- explainable matching;
- подача, просмотр и отзыв заявки;
- рассмотрение заявок владельцем, принятие и отклонение;
- защита от превышения количества мест;
- участие в команде, страница команды, внешний контакт;
- выход из команды и исключение участника;
- жизненный цикл проекта, закрытие набора, отмена проекта.

### 7.2 Не входит в v1

- встроенный чат и сообщения в реальном времени;
- интеграция с Telegram, автоматическое создание чата команды, webhook;
- email-, push- и Telegram-уведомления;
- рейтинг, отзывы, карма, репутация;
- анализ переписки, определение токсичности, sentiment analysis;
- ML-рекомендации и автоматическая проверка навыков;
- процентная формула соответствия;
- внутренние задачи проекта, milestones, task management;
- повторное открытие набора после старта проекта;
- смена роли принятого участника и передача владения проектом;
- самостоятельное добавление навыков пользователями;
- Feature Flags.

Обоснование границы: после формирования команды TeamFinder не должен становиться инструментом управления проектами. Достаточно участия в команде, страницы команды, статуса проекта и внешней ссылки для связи.

## 8. Критерии успеха первой версии

| ID | Критерий |
|---|---|
| SC-1 | Пользователь может пройти путь от регистрации до участия в команде без выхода во внешние инструменты |
| SC-2 | Владелец может создать проект с ролями и получить заявки на конкретные роли |
| SC-3 | Кандидат перед подачей заявки видит, каким требованиям роли он соответствует |
| SC-4 | Превышение количества мест невозможно, в том числе при одновременных действиях |
| SC-5 | Текущее состояние заявки и проекта однозначно понятно обеим сторонам |

## 9. Допущения и ограничения

| ID | Формулировка |
|---|---|
| AS-1 | Пользователи указывают уровни навыков честно; проверка квалификации не выполняется |
| AS-2 | Справочники навыков и типов ролей наполняются командой, а не пользователями |
| AS-3 | Связь внутри команды происходит во внешнем мессенджере |
| AS-4 | Ожидаемая нагрузка первой версии — учебная, оптимизация под высокую нагрузку не требуется |
| CN-1 | Срок первой версии ограничен учебным графиком и контрольными точками |
| CN-2 | Команда состоит из трёх участников с закреплёнными ролями |
| CN-3 | Backend реализуется на C# / ASP.NET Core + EF Core + PostgreSQL |

## 11. Глоссарий

| Термин | Значение |
|---|---|
| Проект | Инициатива, для которой собирается команда |
| Роль проекта | Позиция внутри проекта с требованиями и количеством мест |
| Обязательный навык | Навык, который владелец считает важным для роли |
| Желательный навык | Навык, который является дополнительным преимуществом |
| Заявка | Обращение кандидата на конкретную роль проекта |
| Участие в команде | Факт принадлежности пользователя к команде проекта после принятия заявки |
| Сопоставление | Сравнение профиля пользователя с требованиями роли |
| Набор | Этап жизненного цикла проекта, на котором принимаются заявки |
