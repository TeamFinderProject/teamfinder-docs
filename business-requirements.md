## 2. Описание проблемы

Команду для pet-проектов, хакатонов и учебных проектов сейчас ищут через знакомых, тематические Telegram-чаты, форумы и случайные объявления. Требования к участникам нигде толком не записаны, а отклики теряются в переписке.

Проблема проявляется с двух сторон.

### 2.1 Сторона кандидата

Человек хочет участвовать в проекте, но ему нужен не любой проект, а такой, где:

- тема проекта интересна;
- реально открыта подходящая ему роль;
- его навыки соответствуют требованиям роли.

В объявлении обычно нет структурированных требований, поэтому кандидат не может заранее оценить, подходит ли он, и тратит время на нерелевантные отклики.

### 2.2 Сторона создателя проекта

У автора идеи есть потребность в конкретных специалистах: Backend Developer, Frontend Developer, Designer, DevOps. Ему нужно:

- заранее определить состав ролей и количество мест;
- зафиксировать обязательные и желательные навыки для каждой роли;
- получать отклики именно на конкретную роль;
- сравнивать кандидатов по понятным критериям, а не по свободному тексту сообщения.

### 2.3 Последствия

- долгий и хаотичный подбор участников;
- нерелевантные отклики;
- потеря заявок в переписке;
- непрозрачный выбор кандидата;
- неясный статус набора — непонятно, открыт он или уже закрыт.

## 3. Пользователи и заинтересованные лица

| Роль | Описание | Основной интерес |
|---|---|---|
| Кандидат | Зарегистрированный пользователь, который ищет проект и подаёт заявки | Найти подходящий проект и роль, понимать свои шансы |
| Владелец проекта | Пользователь, создавший проект | Собрать команду под конкретные роли и требования |
| Участник команды | Кандидат, принятый на роль | Видеть состав команды, статус проекта, способ связи; узнавать о событиях без захода на сайт |
| Гость | Незарегистрированный посетитель | Понять, что за сервис, и зарегистрироваться |

Роли не являются взаимоисключающими: один и тот же пользователь может быть владельцем одного проекта и кандидатом в другом.

Владелец проекта и участник команды — разные понятия. Владелец не занимает место в наборе автоматически.

## 5. Бизнес-требования

### 5.1 Профиль и навыки

| ID | Требование | Версия |
|---|---|---|
| BR-1 | Пользователь должен иметь профиль с информацией о себе, интересующими ролями и навыками | MVP |
| BR-2 | Для каждого навыка пользователь указывает уровень владения: начинающий, средний, продвинутый | MVP |
| BR-3 | Уровень навыка является самооценкой пользователя и не проверяется системой | MVP |
| BR-4 | Навыки и типы ролей выбираются из общего справочника; произвольные навыки в первой версии не создаются | MVP |

### 5.2 Проекты и роли

| ID | Требование | Версия |
|---|---|---|
| BR-5 | Пользователь создаёт проект за один шаг: название, описание, тип, внешний контакт команды и сразу список ролей с навыками. Роли можно добавить и позже | MVP |
| BR-6 | Поддерживаемые типы проектов: pet-проект, хакатон, учебный проект | MVP |
| BR-7 | Требования к участникам задаются на уровне роли проекта, а не на уровне проекта целиком. Роль выбирается из справочника типов ролей | MVP |
| BR-8 | Для роли указываются количество мест, обязательные и желательные навыки, при необходимости минимальный уровень навыка | MVP |
| BR-9 | Роль может быть создана без обязательных навыков | MVP |
| BR-10 | Проект должен иметь явное состояние жизненного цикла, определяющее доступные действия | MVP |

### 5.3 Поиск и сопоставление

| ID | Требование | Версия |
|---|---|---|
| BR-11 | Пользователь должен видеть каталог проектов с фильтрами по роли, навыку, типу проекта и открытости набора | MVP |
| BR-12 | Система должна сопоставлять профиль пользователя с требованиями конкретной роли | MVP |
| BR-13 | Результат сопоставления должен быть объяснимым: по каждому обязательному и желательному навыку видно совпадение | MVP |
| BR-14 | Сопоставление носит рекомендательный характер и не блокирует подачу заявки | MVP |
| BR-15 | В первой версии не используются машинное обучение и процентная оценка соответствия | MVP |

### 5.4 Заявки и команда

| ID | Требование | Версия |
|---|---|---|
| BR-16 | Кандидат подаёт заявку на конкретную роль конкретного проекта и может приложить комментарий | MVP |
| BR-17 | Владелец видит профиль кандидата, его навыки, уровни, комментарий и результат сопоставления | MVP |
| BR-18 | Владелец принимает или отклоняет заявку; решение принимает человек, а не система | MVP |
| BR-19 | Кандидат может отозвать свою заявку, пока она ожидает решения. После решения владельца отозвать нельзя, принятый участник может выйти из команды | MVP |
| BR-20 | Заявка и участие в команде — разные сущности; история заявок сохраняется | MVP |
| BR-21 | Количество принятых участников на роль не может превышать количество мест | MVP |
| BR-22 | Участник может выйти из команды, владелец может исключить участника | MVP |
| BR-23 | Принятый участник получает доступ к странице команды и внешнему контакту | MVP |
| BR-24 | Встроенный чат не реализуется; связь команды осуществляется по внешней ссылке | MVP |
| BR-25 | Пользователь видит список своих заявок и их текущие статусы | MVP |
| BR-26 | Владелец видит количество новых заявок по своим проектам | MVP |
| BR-27 | Пользователь может указать ссылки на GitHub и на портфолио | MVP |

## 6. Ценность объяснимого сопоставления

Ключевая особенность TeamFinder — объяснимое сопоставление вместо непрозрачной оценки.

Вместо показателя вида «87% соответствия» пользователь видит разбор по критериям:

```
Обязательные навыки:
  C#          — есть, уровень достаточный
  PostgreSQL  — есть, уровень достаточный
Желательные навыки:
  Docker      — есть
  Redis       — нет
Итог: 2 из 2 обязательных, 1 из 2 желательных
```

Почему это выбрано для первой версии:

- пользователь понимает, чего именно ему не хватает, и может дополнить профиль;
- владелец проекта видит основание для решения и может сравнивать кандидатов;
- команде не нужно обосновывать формулу, веса и пороги;
- логика реализуема и проверяема без машинного обучения.

Процентная оценка не исключена, но отнесена к будущим версиям.

## 7. Границы первой версии

### 7.1 Входит в v1

- регистрация, вход, выход, права доступа;
- профиль, информация о себе, интересующие роли, навыки и их уровни;
- справочники навыков и типов ролей;
- создание и редактирование проекта, тип проекта, состояние проекта;
- роли проекта, количество мест, обязательные и желательные навыки, минимальный уровень;
- каталог проектов и фильтры;
- объяснимое сопоставление;
- подача, просмотр и отзыв заявки;
- рассмотрение заявок владельцем, принятие и отклонение;
- защита от превышения количества мест;
- участие в команде, страница команды, внешний контакт;
- выход из команды и исключение участника;
- жизненный цикл проекта, закрытие набора, отмена проекта;
- уведомления в сервисе и в Telegram-боте (MVP), по почте и push (v1.0).

### 7.2 Не входит в v1

- встроенный чат и сообщения в реальном времени;
- автоматическое создание чата команды в Telegram (бот только присылает уведомления, чат команда создаёт сама);
- рейтинг, отзывы, карма, репутация;
- анализ переписки, определение токсичности и анализ эмоциональной окраски текста;
- ML-рекомендации и автоматическая проверка навыков;
- процентная формула соответствия;
- внутренние задачи проекта, контрольные этапы и управление задачами;
- повторное открытие набора после старта проекта;
- смена роли принятого участника и передача владения проектом;
- самостоятельное добавление навыков пользователями;
- переключатели функций (Feature Flags).
- восстановление пароля по почте и смена email: не в MVP, можно добавить вместе с почтовыми уведомлениями в v1.0.

Обоснование границы: после формирования команды TeamFinder не должен становиться инструментом управления проектами. Достаточно участия в команде, страницы команды, статуса проекта, внешней ссылки для связи и уведомлений о событиях.

## 8. Критерии успеха первой версии

| ID | Критерий |
|---|---|
| SC-1 | Пользователь может пройти путь от регистрации до участия в команде без выхода во внешние инструменты |
| SC-2 | Владелец может создать проект с ролями и получить заявки на конкретные роли |
| SC-3 | Кандидат перед подачей заявки видит, каким требованиям роли он соответствует |
| SC-4 | Превышение количества мест невозможно, в том числе при одновременных действиях |
| SC-5 | Текущее состояние заявки и проекта однозначно понятно обеим сторонам |
| SC-6 | Владелец узнаёт о новой заявке, а кандидат — о решении без ручной проверки сайта: в Telegram (MVP), на почту (v1.0) |

## 9. Допущения и ограничения

| ID | Формулировка |
|---|---|
| AS-1 | Пользователи указывают уровни навыков честно; проверка квалификации не выполняется |
| AS-2 | Справочники навыков и типов ролей наполняются командой, а не пользователями |
| AS-3 | Связь внутри команды происходит во внешнем мессенджере; TeamFinder только присылает уведомления |
| AS-4 | Ожидаемая нагрузка первой версии — учебная, оптимизация под высокую нагрузку не требуется |
| CN-1 | Срок первой версии ограничен учебным графиком и контрольными точками |
| CN-2 | Команда состоит из трёх участников с закреплёнными ролями |
| CN-3 | Серверная часть реализуется на C# / ASP.NET Core + Entity Framework Core + PostgreSQL |

## 10. Открытые вопросы

| ID | Вопрос | Текущее решение |
|---|---|---|
| OQ-1 | Нужен ли минимальный уровень для каждого обязательного навыка | Поле необязательное |
| OQ-2 | Нужна ли роль владельца внутри участия в команде | В v1 владелец хранится отдельно от участия |
| OQ-3 | Нужна ли автоматическая сортировка каталога по результату сопоставления | В v1 сортировка не обязательна |
| OQ-4 | Как именно задаётся внешний контакт команды | Одно поле со ссылкой, задаётся при создании проекта |
| OQ-5 | Как пользователь привязывает Telegram | Одноразовая ссылка на бота из профиля (сделано в MVP) |

## 11. Глоссарий

| Термин | Значение |
|---|---|
| Проект | Инициатива, для которой собирается команда |
| Роль проекта | Позиция внутри проекта с требованиями и количеством мест |
| Обязательный навык | Навык, который владелец считает важным для роли |
| Желательный навык | Навык, который является дополнительным преимуществом |
| Заявка | Обращение кандидата на конкретную роль проекта |
| Участие в команде | Факт принадлежности пользователя к команде проекта после принятия заявки |
| Сопоставление | Сравнение профиля пользователя с требованиями роли |
| Набор | Этап жизненного цикла проекта, на котором принимаются заявки |
