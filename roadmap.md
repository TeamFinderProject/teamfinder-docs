# TeamFinder — Roadmap и план работ

**Статус:** v1  
**Период:** сентябрь — декабрь 2026  
**Владелец:** Участник 1 — Team Lead / Backend / DevOps  
**Reviewer:** Участник 2 — Project Manager / Database Engineer / System Analyst

## 1. Цель

Roadmap фиксирует основные этапы разработки TeamFinder, порядок выполнения работ, распределение ответственности между участниками команды и зависимости между задачами.

Основной пользовательский сценарий TeamFinder v1:

**пользователь → профиль и навыки → поиск проекта → выбор роли → matching → заявка → решение владельца → формирование команды.**

## 4. Этап 2 — База данных и backend foundation

После согласования ERD начинается реализация persistence-слоя.

Основные задачи:

- подключить PostgreSQL;
- подключить Entity Framework Core;
- создать основные Entity;
- настроить связи;
- создать `DbContext`;
- создать migrations;
- подготовить начальные справочные данные;
- сформировать структуру backend-проекта.

Основные сущности:

`User`, `Profile`, `Skill`, `RoleType`, `UserSkill`, `UserRoleInterest`, `Project`, `ProjectRole`, `RoleSkillRequirement`, `Application`, `Membership`.

Этап зависит от готовности **ERD v1**.

## 7. Этап 5 — Matching

Matching в TeamFinder v1 должен быть объяснимым и рекомендательным.

Он показывает:

- совпавшие обязательные навыки;
- отсутствующие обязательные навыки;
- совпавшие дополнительные навыки;
- соответствие уровня навыков требованиям роли.

В v1 не используются:

- Machine Learning;
- сложные рейтинговые модели;
- непрозрачный процент соответствия;
- автоматическое принятие решения за владельца проекта.

---

## 8. Этап 6 — Applications

Пользователь может:

- подать заявку на роль;
- добавить комментарий;
- посмотреть свои заявки;
- отозвать ожидающую заявку.

Владелец проекта может:

- посмотреть заявки;
- принять заявку;
- отклонить заявку.

Состояния заявки:

`PENDING`, `ACCEPTED`, `REJECTED`, `WITHDRAWN`, `CLOSED`

Основные правила:

- одна заявка пользователя на конкретную ProjectRole;
- можно подаваться на разные роли одного проекта;
- Application не занимает место в команде;
- место занимает Membership;
- нельзя принять пользователя, если capacity заполнен;
- принятие заявки создаёт Membership;
- после принятия на одну роль остальные ожидающие заявки пользователя в этом проекте закрываются.

---

## 9. Этап 7 — Team / Membership

Необходимо реализовать:

- просмотр состава команды;
- создание Membership после принятия заявки;
- отображение роли участника;
- выход участника из команды;
- удаление участника владельцем;
- внешний способ связи с участниками.

Встроенный чат в TeamFinder v1 не входит.

---

## 10. Этап 8 — Интеграция frontend и backend

Frontend подключается к реальным API endpoint'ам.

Проверяется основной сценарий:

`Регистрация → Профиль → Каталог → Проект → Matching → Application → Team`

Также проверяются негативные сценарии:

- пользователь не авторизован;
- недостаточно прав;
- объект не найден;
- повторная заявка;
- заполненная роль;
- некорректное состояние проекта;
- запрещённое изменение требований роли;
- превышение capacity.
