## 3. Основные сценарии

### UC-01. Регистрация

| Поле | Значение |
|---|---|
| Основной актор | Гость |
| Предусловия | Пользователь не авторизован |
| Триггер | Гость открывает форму регистрации |
| Постусловия | Создана учётная запись и пустой профиль |

Основной поток:

1. Гость открывает форму регистрации.
2. Гость вводит регистрационные данные и пароль.
3. Система проверяет корректность данных и уникальность учётной записи.
4. Система создаёт учётную запись и связанный с ней профиль одной транзакцией.
5. Система выдаёт access token и refresh token (как при входе, UC-02) и открывает профиль.

API: `POST /api/auth/register`.

Альтернативные потоки:

- 3a. Данные некорректны — система показывает ошибки полей, регистрация не выполняется.
- 3b. Учётная запись уже существует — система сообщает об этом и предлагает выполнить вход.

Связанные правила: RULE-SEC-01, RULE-SEC-02.

---

### UC-02. Вход в систему

| Поле | Значение |
|---|---|
| Основной актор | Гость |
| Предусловия | Учётная запись существует |
| Триггер | Гость открывает форму входа |
| Постусловия | Пользователь авторизован |

Основной поток:

1. Гость вводит email и пароль.
2. Система проверяет пароль по хешу.
3. Система выдаёт access token (JWT, 15 минут) в ответе и refresh token (14 дней) в HttpOnly-cookie.
4. Пользователь попадает в каталог проектов.
5. Когда access token истекает, frontend незаметно для пользователя получает новый по refresh token (`POST /api/auth/refresh`). При перезагрузке страницы сессия восстанавливается так же.

API: `POST /api/auth/login`, `POST /api/auth/refresh`, `POST /api/auth/logout`. Решение описано в `adr-001-authentication.md`.

Альтернативные потоки:

- 2a. Данные неверны — система показывает общее сообщение об ошибке без уточнения, какое именно поле неверно.
- 2b. Больше 10 попыток входа за минуту с одного адреса — система временно отказывает (`429 TOO_MANY_ATTEMPTS`), можно повторить через минуту.

### UC-03. Редактирование профиля

| Поле | Значение |
|---|---|
| Основной актор | Пользователь |
| Предусловия | Пользователь авторизован |
| Триггер | Пользователь открывает свой профиль |
| Постусловия | Профиль обновлён |

Основной поток:

1. Пользователь открывает свой профиль.
2. Пользователь заполняет информацию о себе.
3. Пользователь выбирает интересующие роли из справочника типов ролей.
4. Пользователь добавляет навыки из справочника навыков и указывает уровень по каждому: начинающий, средний, продвинутый.
5. Пользователь сохраняет изменения.
6. Система валидирует данные и сохраняет профиль.

Альтернативные потоки:

- 4a. Навык уже добавлен — система не создаёт дубликат, предлагает изменить уровень.
- 6a. Данные некорректны — изменения не сохраняются, показываются ошибки.

Связанные правила: RULE-PROF-01, RULE-PROF-02.

### UC-04. Создание проекта

| Поле | Значение |
|---|---|
| Основной актор | Пользователь |
| Предусловия | Пользователь авторизован |
| Триггер | Пользователь нажимает «Создать проект» |
| Постусловия | Создан проект с ролями и требованиями к навыкам; пользователь стал владельцем |

Основной поток:

1. Пользователь открывает форму создания проекта.
2. Пользователь указывает название, описание и тип проекта.
3. При необходимости пользователь указывает внешний контакт команды.
4. Пользователь добавляет роли: для каждой выбирает тип роли из справочника, указывает количество мест, обязательные и желательные навыки (шаги UC-05 внутри той же формы).
5. Пользователь нажимает «Создать проект».
6. Система проверяет все поля проекта и ролей и создаёт проект, роли и требования одной транзакцией в состоянии «черновик». Если отмечено «Сразу открыть набор», проект переходит в «набор участников».
7. Система открывает страницу проекта.

Альтернативные потоки:

- 2a. Обязательные поля не заполнены — ошибки показываются у полей, ничего не создаётся.
- 4a. Роли не добавлены — проект создаётся черновиком, роли добавляются позже (UC-05).
- 6a. Ошибка в одной из ролей (например, мест 0) — не создаётся ничего, ошибка показывается в карточке этой роли.
- 6b. Отмечено «Сразу открыть набор», но ролей нет — система отказывает, предлагает добавить роль.

API: `POST /api/projects` (поле `roles`).

Связанные правила: RULE-PROJ-01, RULE-LIFE-01, RULE-LIFE-02, RULE-ROLE-01…04.

### UC-05. Создание роли проекта

| Поле | Значение |
|---|---|
| Основной актор | Владелец проекта |
| Предусловия | Проект существует, пользователь является его владельцем |
| Триггер | Владелец добавляет роль в форме создания проекта (UC-04) или на странице существующего проекта |
| Постусловия | Роль создана и привязана к проекту |

Основной поток:

1. Владелец открывает свой проект и выбирает добавление роли.
2. Владелец выбирает тип роли из справочника.
3. Владелец указывает описание и количество мест.
4. Владелец выбирает обязательные навыки и при необходимости минимальный уровень по ним.
5. Владелец выбирает желательные навыки.
6. Система валидирует данные и сохраняет роль.

Альтернативные потоки:

- 3a. Количество мест меньше одного — система отклоняет сохранение.
- 4a. Обязательные навыки не выбраны — роль сохраняется, это допустимо.
- 6a. Навык указан одновременно как обязательный и желательный — система отклоняет сохранение.

API: в составе `POST /api/projects` или отдельно `POST /api/projects/{projectId}/roles`.

Связанные правила: RULE-ROLE-01, RULE-ROLE-02, RULE-ROLE-04.

### UC-06. Просмотр каталога проектов

| Поле | Значение |
|---|---|
| Основной актор | Пользователь |
| Предусловия | Пользователь авторизован |
| Триггер | Пользователь открывает каталог |
| Постусловия | Пользователю показан отфильтрованный список проектов |

Основной поток:

1. Пользователь открывает каталог проектов.
2. Система показывает проекты, доступные для просмотра.
3. Пользователь ищет по названию и описанию и задаёт фильтры: тип роли, навык, тип проекта, открытость набора. Список выводится страницами по 10.
4. Система применяет фильтры и обновляет список.
5. Пользователь открывает карточку интересующего проекта.

Альтернативные потоки:

- 4a. Под условия фильтра ничего не подходит — система показывает пустое состояние с подсказкой изменить фильтры.

Связанные правила: RULE-PROJ-02.

### UC-07. Просмотр соответствия роли

| Поле | Значение |
|---|---|
| Основной актор | Кандидат |
| Предусловия | Пользователь авторизован, открыта страница проекта с ролями |
| Триггер | Пользователь просматривает роль проекта |
| Постусловия | Пользователю показан разбор соответствия по навыкам |

Основной поток:

1. Пользователь открывает страницу проекта.
2. Система сравнивает профиль пользователя с требованиями роли.
3. Система показывает по каждому обязательному навыку: есть ли навык у пользователя и достаточен ли уровень.
4. Система показывает по каждому желательному навыку факт наличия.
5. Система показывает итог: сколько обязательных и желательных навыков совпало, совпадает ли интересующая пользователя роль с типом роли проекта.

Альтернативные потоки:

- 2a. В профиле нет навыков — система не считает соответствие, а пишет, что сравнивать не с чем, и предлагает заполнить профиль.
- 5a. Соответствие неполное — подача заявки остаётся доступной.

Связанные правила: RULE-MATCH-01, RULE-MATCH-02, RULE-MATCH-03.

### UC-08. Подача заявки на роль

| Поле | Значение |
|---|---|
| Основной актор | Кандидат |
| Предусловия | Проект находится в состоянии набора, роль не закрыта и не заполнена, у пользователя нет заявки на эту роль |
| Триггер | Пользователь нажимает «Откликнуться» на конкретной роли |
| Постусловия | Создана заявка в статусе «ожидает решения» |

Основной поток:

1. Пользователь на странице проекта выбирает конкретную роль этого проекта.
2. Пользователь нажимает «Откликнуться», открывается модальное окно S-04a.
3. Пользователь при желании пишет комментарий к заявке.
4. Пользователь отправляет заявку.
5. Система проверяет состояние проекта, состояние роли и отсутствие предыдущей заявки на эту роль.
6. Система создаёт заявку в статусе «ожидает решения».
7. Система показывает подтверждение и отражает заявку в списке заявок пользователя.

Альтернативные потоки:

- 5a. Проект не находится в состоянии набора — заявка отклоняется с соответствующей ошибкой.
- 5b. Все места роли заняты — заявка отклоняется с ошибкой заполненности роли.
- 5c. У пользователя уже есть заявка на эту роль (в любом статусе) — повторная подача запрещена.
- 5d. Пользователь является владельцем проекта — подача заявки запрещена.
- 5e. Пользователь уже состоит или раньше состоял в команде этого проекта — подача запрещена (в v1 вернуться после выхода нельзя).

Заявка относится к роли внутри проекта: на разные роли одного проекта можно подать отдельные заявки.

API: `POST /api/projects/{projectId}/roles/{roleId}/applications`.

Связанные правила: RULE-APP-01, RULE-APP-02, RULE-APP-06, RULE-APP-08, RULE-CAP-02.

### UC-09. Отзыв заявки

| Поле | Значение |
|---|---|
| Основной актор | Кандидат |
| Предусловия | Заявка существует и находится в статусе «ожидает решения» |
| Триггер | Пользователь отзывает заявку в списке своих заявок |
| Постусловия | Заявка переведена в статус «отозвана» |

Основной поток:

1. Пользователь открывает список своих заявок.
2. Пользователь выбирает заявку в статусе «ожидает решения».
3. Пользователь подтверждает отзыв.
4. Система переводит заявку в статус «отозвана».

Альтернативные потоки:

- 3a. Заявка уже обработана владельцем — отзыв невозможен, система показывает актуальный статус.
- 3b. Заявка принята — кнопка «Отозвать» отключена с подсказкой; чтобы уйти из проекта, участник выходит из команды (UC-13).

Отзыв возможен только в статусе «ожидает решения». Других условий нет: ожидающая заявка существует только пока идёт набор.

API: `POST /api/applications/{applicationId}/withdraw`.

Связанные правила: RULE-APP-03, RULE-APP-05, RULE-PERM-03.

### UC-10. Просмотр заявок на проект

| Поле | Значение |
|---|---|
| Основной актор | Владелец проекта |
| Предусловия | Пользователь является владельцем проекта |
| Триггер | Владелец открывает раздел заявок своего проекта |
| Постусловия | Владельцу показан список заявок с данными кандидатов |

Основной поток:

1. Владелец открывает раздел заявок проекта.
2. Система показывает заявки, сгруппированные по ролям.
3. Владелец открывает заявку и видит профиль кандидата, информацию о себе, навыки и уровни, интересующие роли, комментарий к заявке, результат сопоставления и текущий статус заявки.

Альтернативные потоки:

- 2a. Заявок нет — показывается пустое состояние.
- 1a. Пользователь не является владельцем проекта — доступ запрещён.

Связанные правила: RULE-PERM-02.

### UC-11. Принятие заявки

| Поле | Значение |
|---|---|
| Основной актор | Владелец проекта |
| Предусловия | Проект в состоянии набора, заявка в статусе «ожидает решения», на роли есть свободное место |
| Триггер | Владелец нажимает «Принять» |
| Постусловия | Заявка принята, создано участие в команде, количество свободных мест уменьшено |

Основной поток:

1. Владелец открывает заявку.
2. Владелец нажимает «Принять».
3. Система проверяет наличие свободного места на роли.
4. Система переводит заявку в статус «принята».
5. Система создаёт участие пользователя в команде проекта.
6. Система закрывает остальные ожидающие заявки этого пользователя в данном проекте.
7. Если все места роли заняты, роль больше не принимает заявки, а остальные ожидающие заявки на неё закрываются (причина «все места заняты»).
8. Кандидат получает доступ к странице команды и внешнему контакту.

Альтернативные потоки:

- 3a. Свободных мест нет — система отклоняет действие с ошибкой заполненности роли.
- 3b. Два принятия последнего места выполняются одновременно — система выполняет их по очереди и принимает только одного кандидата. Второе принятие получает ошибку: его заявка уже закрыта, потому что мест не осталось.
- 2a. Проект не находится в состоянии набора — принятие запрещено.

Связанные правила: RULE-CAP-01, RULE-CAP-03, RULE-APP-04, RULE-TEAM-01.

### UC-12. Отклонение заявки

| Поле | Значение |
|---|---|
| Основной актор | Владелец проекта |
| Предусловия | Заявка в статусе «ожидает решения» |
| Триггер | Владелец нажимает «Отклонить» |
| Постусловия | Заявка переведена в статус «отклонена» |

Основной поток:

1. Владелец открывает заявку.
2. Владелец нажимает «Отклонить».
3. Система переводит заявку в статус «отклонена».
4. Кандидат видит изменение статуса в списке своих заявок и получает уведомление.

Альтернативные потоки:

- 2a. Заявка уже отозвана кандидатом — действие недоступно, показывается актуальный статус.

Связанные правила: RULE-APP-05, RULE-APP-06.

### UC-13. Выход из команды

| Поле | Значение |
|---|---|
| Основной актор | Участник команды |
| Предусловия | Пользователь является участником команды проекта |
| Триггер | Участник выбирает выход на странице команды |
| Постусловия | Участие прекращено, доступ к закрытой информации снят |

Основной поток:

1. Участник открывает страницу команды.
2. Участник выбирает выход из команды и подтверждает действие.
3. Система прекращает участие.
4. Если проект находится в состоянии набора, место на роли освобождается.
5. Система снимает доступ к внешнему контакту команды.

Альтернативные потоки:

- 4a. Проект уже переведён в работу — состав команды уменьшается, набор автоматически не открывается.
- 2a. Проект завершён или отменён — состав команды больше не меняется, выйти нельзя.

Связанные правила: RULE-TEAM-02, RULE-TEAM-04, RULE-LIFE-05.

### UC-14. Исключение участника

| Поле | Значение |
|---|---|
| Основной актор | Владелец проекта |
| Предусловия | В команде есть участник |
| Триггер | Владелец выбирает исключение участника |
| Постусловия | Участие прекращено |

Основной поток:

1. Владелец открывает страницу команды.
2. Владелец выбирает участника и подтверждает исключение.
3. Система прекращает участие.
4. Если проект находится в состоянии набора, место освобождается.
5. Система снимает у исключённого пользователя доступ к закрытой информации проекта.

Альтернативные потоки:

- 2a. Проект завершён или отменён — состав команды больше не меняется, исключить нельзя.

Связанные правила: RULE-TEAM-03, RULE-TEAM-04, RULE-PERM-02, RULE-LIFE-05.

### UC-15. Перевод проекта в работу

| Поле | Значение |
|---|---|
| Основной актор | Владелец проекта |
| Предусловия | Проект находится в состоянии набора |
| Триггер | Владелец закрывает набор |
| Постусловия | Проект переведён в состояние «в работе», новые заявки запрещены |

Основной поток:

1. Владелец открывает свой проект.
2. Владелец выбирает перевод проекта в работу.
3. Система переводит проект в состояние «в работе».
4. Система закрывает все ожидающие заявки по проекту.
5. Система запрещает подачу новых заявок.

Альтернативные потоки:

- 2a. Заполнены не все роли — перевод в работу всё равно разрешён.
- 3a. Проект находится в черновике — сначала требуется открыть набор.

Связанные правила: RULE-LIFE-02, RULE-LIFE-03, RULE-APP-07.

### UC-16. Завершение или отмена проекта

| Поле | Значение |
|---|---|
| Основной актор | Владелец проекта |
| Предусловия | Проект не находится в конечном состоянии |
| Триггер | Владелец выбирает завершение или отмену проекта |
| Постусловия | Проект переведён в состояние «завершён» или «отменён» |

Основной поток:

1. Владелец открывает свой проект.
2. Владелец выбирает завершение или отмену проекта и подтверждает действие.
3. Система переводит проект в выбранное конечное состояние.
4. Система закрывает все ожидающие заявки по проекту.
5. Проект становится недоступным для новых заявок, данные команды сохраняются как история.

Альтернативные потоки:

- 2a. Завершить можно только проект в работе. Черновик и проект в наборе можно только отменить.

Связанные правила: RULE-LIFE-04, RULE-APP-07.

### UC-17. Просмотр уведомлений

| Поле | Значение |
|---|---|
| Основной актор | Пользователь |
| Предусловия | Пользователь авторизован |
| Триггер | В шапке появилось число непрочитанных уведомлений |
| Постусловия | Уведомления отмечены прочитанными |

Основной поток:

1. Система при событиях (новая заявка, решение по заявке, закрытие заявки, выход или исключение участника, смена состояния проекта) создаёт уведомление адресату.
2. Пользователь открывает список уведомлений.
3. Пользователь переходит по уведомлению к проекту.
4. Система отмечает открытое уведомление прочитанным. Кнопка «Прочитать все» отмечает все сразу.

Если пользователь подключил Telegram (UC-18), те же уведомления приходят в чат с ботом. Почта и push — к v1.0.

API: `GET /api/notifications`, `POST /api/notifications/{notificationId}/read`, `POST /api/notifications/read-all`.

Связанные правила: RULE-NOTIF-01, RULE-NOTIF-02.

### UC-18. Подключение Telegram-уведомлений

| Поле | Значение |
|---|---|
| Основной актор | Пользователь |
| Второстепенный актор | Telegram |
| Предусловия | Пользователь авторизован, бот настроен на сервере |
| Триггер | Пользователь нажимает «Подключить Telegram» в профиле |
| Постусловия | Уведомления пользователя приходят в Telegram |

Основной поток:

1. Пользователь открывает профиль и нажимает «Подключить Telegram».
2. Система создаёт одноразовый код на 10 минут и показывает ссылку на бота.
3. Пользователь открывает ссылку и нажимает Start в Telegram.
4. Бот получает код, система связывает чат с аккаунтом и отвечает «Готово».
5. Новые уведомления пользователя приходят в чат с ботом.

Альтернативные потоки:

- 2a. Бот не настроен на сервере — система сообщает, что Telegram недоступен, уведомления остаются на сайте.
- 4a. Ссылка просрочена или уже использована — бот предлагает получить новую в профиле.
- 5a. Пользователь отключает уведомления кнопкой «Отключить» в профиле или командой `/stop` в чате.

API: `GET /api/profile/telegram`, `POST /api/profile/telegram/link`, `DELETE /api/profile/telegram`.

Связанные правила: RULE-NOTIF-03, RULE-NOTIF-04.
